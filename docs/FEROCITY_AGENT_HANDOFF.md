## 2. Product definition and non-negotiable rules

Ferocity is an AI operating system for running and growing a business. It combines shared business context, business records, permissions, controlled execution, communications, operations, money, workforce, growth, measurement, and an owner command layer.

Product rules:

- Ferocity is for contractor/field-service companies and professional/white-collar businesses; do not reduce the core brand to either category.
- It is more than a tool collection and more than advice. Ferocity should identify bottlenecks/opportunities, propose a plan, perform authorized work, surface exceptions, measure business outcomes, and learn.
- The in-app Ferocity conversation is the main operating interface, but conventional dashboards and direct controls remain available.
- Native AI Workforce roles are coordinated workflows over shared context, tools, and action contracts. Do not fake independent agents or “agent theater.”
- Ferocity is agent/provider agnostic. Native AI and future outside agents (OpenAI, Grok/xAI, Gemini, Claude, specialized providers) should use the same permissioned business-action layer.
- Ferocity remains the system of record/control layer: identity, tenant boundaries, permissions, approvals, business state, audit logs, attribution, budgets, and safety stay inside Ferocity.
- Normal customers connect providers by signing in, granting scoped access, and selecting an account. Ferocity owns platform developer apps, OAuth clients, callbacks, webhooks, and provider approval.
- Read-only discovery comes first. Public posts, messages, calls, campaign writes, spend, billing, money movement, destructive actions, and low-confidence actions require explicit policy/approval.
- Capability and connector statuses must be honest, runtime-driven where possible, and changeable without a new deploy after the status framework itself is deployed.
- Do not expose proprietary prompts, scoring, orchestration, schemas, or implementation details on public pages. Explain outcomes, controls, proof, and customer-facing capability.
- Preserve audit evidence and originals for documents, communications, provider events, expenses, and material actions.
- Ferocity's entire operating brain improves companion products: business context and memory, reasoning, goals, planning, workflows, AI workforce coordination, permissions, approvals, integrations, exception handling, measurement, and learning. This is broader than reusing OCR or individual features. Ferocity does not need to own or duplicate the companion product's domain data; that product remains authoritative, and every write-back uses an explicit adapter, existing workflow, idempotency, audit evidence, and the same approval boundary the product already requires.
- Homes4Rent specifically remains authoritative for properties, units, tenants, leases, notices, rent/payment accounting, and signature evidence. Ferocity may analyze and prepare around those records, but must not replace or casually modify H4R's schema or financial/signing semantics.
- Never fabricate reviews, engagement, leads, results, activity, or rankings; never spam communities; follow provider policies.

## 7. Deployment, database, and release workflow

Local setup:

```powershell
npm ci
Copy-Item .env.example .env.local # then populate securely; never commit
npm run dev
```

`db:validate:migrations` is a mutating, disposable-database-only compatibility check. It does not read `DATABASE_URL`, `.env.local`, or `.env`; default `predeploy:local` therefore refuses at this gate before creating a database client. Inject the dedicated URL through approved secret tooling, then acknowledge the nonsecret identity derived from that URL:

```powershell
$env:MIGRATION_VALIDATION_DATABASE_URL = $approvedDisposableDatabaseUrl
$env:MIGRATION_VALIDATION_DISPOSABLE_ACK = "disposable:<host>:<effective-port>/<encoded-database>#route=<sha256>"
npm run db:validate:migrations
```

The validator reports the exact required nonsecret acknowledgement when it refuses a missing or mismatched value, before constructing a database client. Its SHA-256 routing fingerprint binds the URL authority's host, effective port (explicit or 5432), database, and username without printing the username, password, or full URL. The URL must explicitly contain host, database, username, and password; query-string routing overrides are rejected, and only `sslmode=require` is accepted. The same parsed routing fields are passed explicitly to PostgreSQL so inherited `PGHOST`, `PGPORT`, `PGDATABASE`, and `PGUSER` values cannot redirect the check. The acknowledgement is operator confirmation, not technical proof that the target is disposable. The command executes pending SQL inside a bounded rollback transaction; rollback is attempted but cannot guarantee the absence of every side effect. Never point it at production. Confirm that the disposable target's `public.schema_migrations` history is readable and represents the intended baseline before running it. Supply the same two variables when running the complete `predeploy:local` gate.

Common focused checks:

```powershell
npm test -- --run <test-files>
npm run typecheck
npm run lint
npm run provider:truth
npm run capability:truth
npm run public:claims

```
